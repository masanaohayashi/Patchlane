# 実装構成

- `Sources/Patchlane`: SwiftUI画面、設定保存、機器音量、通常／専用モードのライフサイクル。
- `Sources/AudioCore`: C++のAUHALミキサー、共有音声からの時刻指定読み取り。専用出力は共有リングのみを使う。
- `Driver`: 2ch／8ch AudioServerPlugIn。音量・ミュート・ルーティングを処理する。
- `Shared`: 時刻付き音声リング、クロック、補間、読み取り専用Machメモリ共有、認証プロトコル。
- `Broker`: 専用ドライバー内部の補助サービス。2ch／8chの共有領域を別々に管理する。音声コピーは行わない。
- `Uninstaller`: 管理者認証付き削除アプリ。製品IDを検証して対象ファイルだけを削除する。

音声コールバック内でメモリ確保、ロック、ファイルI/O、Swift処理を行わない設計とする。接続・切断・署名検証は制御スレッドで行う。

共有リングは保持容量であり、一定量を蓄積してから再生するキューではない。必要な時刻のデータがない場合は無音となる。物理機器とのクロック差には補間を使用する。

通常ミキサーと専用出力は同時に同じ経路を再生しない。切り替え時は停止と機器設定の復元を完了してから次の経路を開始する。

UIはメインスレッド、機器の開始・停止・設定復元は直列制御キュー、設定保存はutilityキューで処理する。開始・停止の完了は世代番号で照合し、古い開始結果で状態を上書きしない。終了時だけ制御キューを待って後始末する。

音声処理はCore AudioのAUHAL／IOProcスレッド上のC++のみ。UIとの受け渡しは常にlock-freeなatomic値と固定容量リングを使う。設定スナップショットは一度だけ読み、書き込みと競合した場合は前の完全な設定を使う。メーター更新も一度だけ試し、再試行しない。ドライバーの制御側mutexはプロパティ更新・開始停止に限り、音声処理と時刻取得から取得しない。

通常モードの音声設定の変更検知は`AudioSettings`の値の等価比較で行う。JSONエンコード結果はキー順が一定ではないため、変更検知には使わない。制御側でも`MixerConnectionSettings`を比較し、同じ接続への再設定で音声を停止しない。HAL機器列挙と音量取得・変更は直列制御キューで行い、メインスレッドは結果の表示だけを担当する。定期問い合わせは各種類につき一件だけ実行し、滞留を防ぐ。

画面の設定は両モードで同じ`Settings`を使う。専用モードは入力1のみを使い、入力2〜4の保存設定を保持して無効にする。最大4出力が同じ共有音声を読み、各出力コールバックで入力ゲイン・ルート・ミュートを適用する。入出力メーターは音声サンプルから計測し、atomicでUIへ渡す。HALのミックス設定は接続中だけ等倍・同一チャンネルにし、停止時に変更がなければ元へ戻す。複数出力の機器設定は接続の逆順に復元する。

追加バッファ数は0〜8。`追加バッファ数 × サンプルバッファ長`を遅延フレーム数とする。通常モードは読み取り位置をその分だけ後ろに取り、専用モードは物理出力時刻からその分だけ遡った音声を読む。0は追加バッファなしであり、総遅延ゼロを意味しない。
